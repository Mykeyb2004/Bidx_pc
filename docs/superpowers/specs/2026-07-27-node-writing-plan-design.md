# 节点撰写计划与提示词拼接设计

## 目标

为投标大纲节点增加可持久化的撰写计划。系统从独立 JSON 文件读取节点计划，在单章节扩写窗口现有“附加扩写要求”输入框中展示；用户修改后可写回原文件。生成提示词时，该输入框内容统一解释为“节点撰写计划”，用于指导当前节点正文的组织和展开，不再作为另一类通用附加要求处理。

同时调整提示词的阅读顺序和冲突说明，使模型先明确当前章节边界及招标/评分要求，再接收输出硬约束提醒、事实材料和节点撰写计划，最后由章节任务卡收束任务重点。

## 术语与语义

- “附加扩写要求”是现有 UI 输入框名称。
- 该输入框在本功能中的业务内容就是“节点撰写计划”，二者不是两套可叠加的数据。
- 模型提示词中统一使用“节点撰写计划”，不再输出“用户附加要求”标题。
- 节点撰写计划是当前节点的局部执行蓝图，不是新的招标事实来源，也不能突破章节边界、招标/评分要求或输出硬约束。
- 未匹配到计划时保持现有扩写行为，不注入空标题或占位说明。

## 配置与数据文件

在项目输入配置中增加可选字段：

```yaml
project:
  inputs:
    writing_plan_file: "./撰写计划.json"
```

相对路径按项目根目录 `project.root_dir` 解析。文件结构固定为：

```json
{
  "version": 1,
  "items": [
    {
      "node": "2.3.1",
      "writing_plan": "先回应评分点，再按实施步骤、责任分工和成果佐证展开。"
    }
  ]
}
```

约束如下：

- `version` 当前只接受整数 `1`。
- `node` 为大纲 Markdown 标题文本开头的章节编号，例如 `2.3.1`。
- 节点编号采用精确匹配，不继承父节点计划，也不进行标题模糊匹配。
- 同一文件中 `node` 不得重复。
- `writing_plan` 保存输入框的完整文本，保留换行。
- 保存空内容表示删除对应节点记录。
- 未配置文件时完全保留旧行为；配置了文件但文件不存在时按空计划库处理，第一次保存非空计划时创建文件。
- 写回使用 UTF-8、无 BOM、两空格缩进和 `ensure_ascii: false`；更新已有节点时保持其列表位置，新节点追加到末尾，删除节点时不重排其他记录。
- 实现时同步维护 `docs/config_schema.md`、`config.example.yaml`、相关 `config_*.yaml` 和测试夹具。

## 组件边界

新增独立 `WritingPlanStore`，负责：

- 解析和校验 JSON 文件；
- 按节点编号查询计划；
- 新增、更新和删除计划；
- 原子写回文件；
- 检测文件在加载后是否被外部修改。

GUI、`HeadingNode` 和 `AIWriter` 不直接操作 JSON。`HeadingNode` 继续只表示大纲结构，不增加持久化计划字段。GUI 通过 `WritingPlanStore` 读取和保存文本，再把最终文本作为当前扩写调用的 `additional_requirements` 参数传入；该参数可暂时保留内部名称以控制改动范围，但其业务语义改为节点撰写计划。

当配置了 `writing_plan_file` 时，停用旧的隐藏式 `ChapterWritingPlanGenerator`，避免同一节点同时出现人工计划和模型自动计划。未配置新文件时，保留旧功能的兼容行为。

## 节点编号提取

从 `HeadingNode.title` 的开头提取章节编号，支持 `1`、`1.2`、`1.2.3` 等点分数字形式。编号后必须是标题结束、空白，或 `.、:：-` 之一；单独的尾随 `.` 只作为标题分隔符，不计入节点编号。匹配使用规范化后的数字点分值，例如标题 `1.4.2 进场核验...` 对应键 `1.4.2`，标题 `1. 项目实施方案` 对应键 `1`。

标题没有可识别编号时，不读取或写入节点计划，UI 显示“当前节点无可用编号”并禁用“保存撰写计划”。用户仍可在输入框临时输入内容并用于本次扩写；“开始扩写”在该情况下跳过持久化。系统不使用 `full_path`、行号或标题正文作为替代键，避免大纲标题调整后产生不可预测匹配。

## 单章节 UI

继续使用现有“附加扩写要求”多行输入框，不新增第二个计划输入区。窗口打开时：

- 显示当前节点编号；
- 若精确匹配到计划，将其填入输入框；
- 未匹配时保持输入框为空；
- 显示加载状态或明确的读取错误；
- 提供“保存撰写计划”按钮和保存状态；
- 用户编辑后标记为未保存状态。

“开始扩写”先保存当前计划，再启动正文生成。保存失败时不开始扩写，避免模型使用了未持久化、用户却误以为已保存的内容。关闭存在未保存修改的窗口时，提示保存、放弃或取消关闭。

保存空文本会删除当前节点记录；文件原本不存在且内容为空时不创建空文件。

未配置 `writing_plan_file` 时，输入框继续作为仅用于本次扩写的临时输入，不显示持久化保存状态；配置了文件但节点无编号时按前述无编号规则处理。

## 批量扩写

- 批量窗口显示本次节点中有计划和无计划的覆盖数量。
- 批量开始时加载一次计划文件快照，整批生成使用同一快照，避免生成过程中外部编辑导致前后章节不一致。
- 每个节点按编号精确匹配；未匹配节点不注入计划。
- 批量窗口不提供批量编辑或批量写回计划。
- 快照加载失败时阻止开始批量扩写并显示明确错误。

## 提示词消息层级

模型请求继续使用两条消息：

```text
system message: 角色设定 + 完整输出硬约束
user message: 当前章节上下文 + 节点撰写计划 + 章节任务卡
```

真正的 `system` 消息不能移动到 `user` 消息之后。API 的消息角色决定它始终具有更高指令优先级；把硬约束改成普通 user 文本会降低约束可靠性。因此，本设计所说的“移动到当前章节边界及招标/评分要求后面”，是指：

- `system` 消息仍保持独立并正常发送；
- `user` 消息中的“遵守 system 硬约束”短提醒放在章节边界及招标/评分要求之后；
- trace 或组合预览按业务阅读顺序展示，避免让审阅者误以为业务要求被全局格式规则覆盖。

## User Prompt 顺序

`auto` 和 `full_context` 路径统一采用以下业务顺序；没有内容的块直接省略：

```text
## 当前章节边界及招标/评分要求
  相关采购需求或固定参考材料
  必须响应 / 参考评分项
  上级标题、当前标题、同级标题和禁止越界说明

## 输出硬约束提醒
  请严格遵守 system 中全部硬门禁，直接输出当前章节投标正文。
  节点撰写计划和事实材料不得突破本章边界及招标/评分要求。

## 事实卡片参考
  强制事实 / 参考事实及冲突规则

## 节点撰写计划
  来自“附加扩写要求”输入框的完整文本

## 章节任务卡
  写作场景、章节路径、本章重点、篇幅、表格、流程图和输出方式
  最终执行说明
```

章节任务卡保持在最后，用于在长上下文之后重新锚定当前任务。任务卡增加以下语义：

```text
- 执行要求：按照节点撰写计划组织本节点正文；计划未覆盖的必要评分点应补齐，计划与当前章节边界、招标/评分要求或 system 硬约束冲突时不得照搬。
```

没有节点撰写计划时不输出该行，也不改变原任务卡的生成逻辑。

## 内容与格式冲突规则

提示词不使用一条模糊的总优先级同时排序所有材料，而是区分三个维度：

- 内容正确性：以招标需求和评分标准为依据；事实卡片冲突时服从招标/评分要求。
- 章节范围：当前章节边界决定本节点应写和不应写的内容；宽泛评分项只覆盖与本节点直接相关的部分。
- 执行与表达：节点撰写计划决定局部展开路线，system 硬约束决定称谓、编号、禁用表达和输出格式。

`system` 中“最高优先级”的说明限定为输出形式、主体称谓和禁用表达，不声明其覆盖招标事实或评分要求。节点计划中的文字按用户数据处理，不允许其中的指令取消 system 硬约束。

## 针对松滋助联体配置的评估

`config_松滋助联体.yaml` 使用 `processing.path: auto`、启用评分抽取和事实卡片、关闭项目背景、默认目标篇幅 1500 字、表格上限 1、Mermaid 上限 1。现有 `auto` user prompt 的实际顺序是：评分关注、章节边界、事实卡片、硬约束短提醒、用户附加要求、章节任务卡。

以 `1.4.2 进场核验、人员到岗、制度衔接与试运行阶段计划` 的已有生成 trace 为例，当前附加文本“计划要符合项目服务周期的总体安排所规划的阶段时长”已成功影响正文，模型把该节点限定在第 1 个月，并与第 2 个月规范运行阶段建立边界。这说明任务卡置后和事实卡片注入有效。

仍需解决的问题是：

- “用户附加要求”标签把正式节点计划表现为可选补充，语义权重不足；
- `auto` 当前只注入评分关注和章节边界，不稳定注入采购需求摘录，“招标要求”不能在没有材料时虚构为已提供；
- 当前写作依据会提到可能不存在的项目背景，需改为按实际存在的块动态生成；
- 评分抽取可能带入与当前节点间接相关的人员培训、项目负责人等内容，应依靠“必须响应/参考”和章节边界防止展开；
- system 中禁止英文的规则需要明确豁免 Mermaid 等必要技术语法，否则会与流程图要求发生字面冲突；
- 配置中的“禁止自解释”与 system 同类规则重复，最终 prompt 应只保留一份强约束或一条短提醒。

本功能先完成计划语义统一和 prompt 重排，不顺带改造采购需求检索算法。若后续需要让 `auto` 稳定包含采购需求摘录，应作为独立优化验证召回准确性和上下文长度。

## 错误处理与并发保护

- JSON 语法错误、根结构错误、未知版本、重复节点或字段类型错误均显示明确错误，并禁止覆盖原文件。
- 保存采用同目录临时文件、落盘同步和原子替换，避免中途退出产生半写文件。
- 加载时记录文件摘要；保存前重新计算摘要。文件被外部修改时拒绝直接覆盖，提示用户重新加载后合并。
- 首次加载时文件不存在也记录“缺失”快照；若保存前文件已被外部创建，同样按外部修改冲突处理，不覆盖新文件。
- 文件路径不可写、目录不存在且无法创建、编码错误等情况均保留输入框内容，允许用户修复后重试。
- 单章节与批量生成都不得静默忽略一个已配置但损坏的计划文件。

## 测试与验收

- 配置测试覆盖相对路径解析、未配置兼容和示例配置文档。
- `WritingPlanStore` 测试覆盖读取、精确匹配、新增、更新、空值删除、首次创建、重复节点、版本错误、损坏 JSON、原子写入和外部修改冲突。
- 节点编号测试覆盖 H1-H5 常见编号、无编号标题和相似编号不误匹配，例如 `2.3.1` 不匹配 `2.3.10`。
- 单章节 UI 测试覆盖预填、脏状态、显式保存、开始扩写前保存、空值删除、关闭确认和错误展示。
- 批量测试覆盖覆盖率摘要、单次快照、无计划忽略、加载失败阻断和不写回文件。
- prompt 测试覆盖“用户附加要求”不再出现、“节点撰写计划”只出现一次、计划位于任务卡前、任务卡最后、system 短提醒位于章节边界及招标/评分要求之后。
- prompt 冲突测试覆盖计划要求越过同级边界、事实卡与采购需求冲突、Mermaid 技术语法豁免和无计划时完全省略计划块。
- 使用 `config_松滋助联体.yaml` 验收 `1.4.2` 节点时，计划应从 UI 自动加载；扩写正文应继续限定在启动准备阶段，并保持第 1 个月与后续规范运行阶段的边界。

## 不在本次范围

- 父节点计划继承或多层计划合并；
- 按标题正文、路径或行号进行模糊匹配；
- 在批量窗口编辑或批量生成计划；
- 自动改写、总结或优化用户输入的节点计划；
- 为 `auto` 路径新增采购需求检索算法；
- 修改事实卡片的数据结构和选择逻辑。

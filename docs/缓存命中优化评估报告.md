# 章节扩写阶段 Prompt 缓存命中率评估报告

> 分析对象：`bid_writer/ai_writer.py`（提示词拼装与模型请求）、`bid_writer/context_pruner.py`（上下文裁剪）
> 结论先行：问题不是"没开缓存"，而是**请求的 token 前缀在每个章节之间几乎没有公共部分**，导致上游推理服务（vLLM / DeepSeek / 兼容 OpenAI 的网关）的 **prefix/KV 缓存无法命中**。本报告只做评估与建议，不改动代码。

---

## 1. 缓存命中的前提

所有兼容 OpenAI 的推理服务的 prompt 缓存（prefix cache / context cache / KV cache）都遵循同一条规则：

> **只有从第 0 个 token 开始、与上一次请求完全逐字节一致的最长公共前缀，才能被复用。**
> 一旦某个位置的内容发生变化，该位置之后的所有 token 都必须重新计算，缓存失效。

因此命中率取决于一件事：**稳定、可复用的大块内容是否被放在 messages 的最前面，变化的小块内容是否被放在最后面。**

当前代码恰好相反。

---

## 2. 当前请求的实际结构

`prepare_generation()`（`ai_writer.py:1214`）组装的请求是：

```
messages = [
  { role: "system", content: system_prompt },      # 稳定：role + 门禁规则
  { role: "user",   content: prompt }               # 见下方拼装顺序
]
```

`user` 内容由 `build_prompt_result()` 按固定顺序拼接（`ai_writer.py:1054-1091`）：

| 顺序 | 段落 | 稳定性 | 来源 |
|---|---|---|---|
| 1 | `chapter_context`（## 当前章节边界及招标/评分要求） | **高度变化** | 每章不同 |
| 2 | `output_constraint_reminder`（## 输出硬约束提醒） | 稳定（除 extra_rules） | 全局固定 |
| 3 | `fact_card_context` | 变化 | 选中的事实卡 |
| 4 | `node_writing_plan` | 变化 | 节点撰写计划 |
| 5 | `task_card`（## 章节任务卡） | 变化 | 每章路径/焦点/字数 |

关键在于第 1 段 `chapter_context` 内部的构造（`_build_chapter_context_section`, `ai_writer.py:429`）：

```
## 当前章节边界及招标/评分要求
### 招标需求参考      ← 仅 full_context 模式有；pruned 模式为空
### 项目背景参考      ← 按 H2 变化
### 评分要求          ← 按章节检索结果变化（pruned 模式每章不同）
### 当前章节边界      ← scope_reference，每章必不同（父标题/本标题/同级标题）
```

---

## 3. 根因分析（为什么几乎不命中）

### 根因 A：可变内容被放在 user 消息的最前面
`user` 消息第一段就是 `chapter_context`，而它内部**第二行之后就开始出现每章不同的内容**（项目背景、检索到的评分项、章节边界）。这意味着：

- `system` prompt 之后，公共前缀**立刻断裂**。
- 可缓存的前缀实际上只剩下 `system_prompt` 本身 + `"## 当前章节边界及招标/评分要求\n"` 这一行标题。
- `system_prompt` 通常只有几百~一两千 token，相对每次请求的总输入占比很小，缓存收益极低。

### 根因 B：上下文裁剪（pruned/auto 模式）让"稳定大块"消失
在默认的裁剪路径下（`context_pruner.build_context`），`bid_requirements` 和完整 `scoring_criteria` **不进入 prompt**，取而代之的是**每章各异的检索子集**（`scoring_section`）。

- 在 `full_context` 模式下，至少 `### 招标需求参考 + 完整招标需求`（大块、稳定）排在 `chapter_context` 靠前位置，还能形成一段可观的公共前缀；
- 但一旦启用裁剪，这段最大的稳定内容被拿掉，剩下的全是每章不同的小块，**公共前缀被进一步压缩到几乎为零**。

换句话说：裁剪优化了单次请求的 token 数，却**顺带摧毁了跨章节的缓存复用**。两者在当前布局下是互相抵消的。

### 根因 C：同一 H2 下的 H4 章节本可共享的前缀没有被利用
系统已经在 H2 级别缓存了两类昂贵结果（本地缓存，命中良好）：
- `H2ProjectBackgroundGenerator`（项目背景，H2 级）
- `_classify_scoring_with_h2_cache`（评分分类，H2 级）

也就是说，**同一个 H2 下的多个 H4 章节，其"项目背景"和"评分板块归类"是完全相同的**。这是一段天然可复用的、每章之间逐字节一致的内容。但当前布局把它夹在 `chapter_context` 中间、且排在每章不同的 scope_reference 之前，导致这段本可命中的前缀同样无法被上游缓存利用。

### 根因 D：请求里没有任何缓存提示，也没有观测
- `_build_request_options()`（`ai_writer.py:328`）只设置 `model/messages/temperature/max_tokens/stream/top_p/seed/reasoning_effort`，**没有任何 `cache_control` / `extra_body` 缓存开关**。对自动前缀缓存的服务（DeepSeek、多数 vLLM 网关）这不是必需的，但对需要显式声明的服务（如 Anthropic 风格 `cache_control`）则完全没用上。
- trace / timing 日志中**没有记录 `usage.prompt_tokens_details.cached_tokens`** 一类字段（`generation_trace.py`、`timing_logger.py` 均无）。因此目前"缓存几乎没命中"只能靠主观感受，无法量化，也无法验证优化效果——这违反了项目 `Observability` 约束。

### 根因 E：每章的第二次模型调用天然不可缓存
`_request_numbering_structure()`（`ai_writer.py:507`）在正文后处理阶段会用**主模型**再发一次请求，其 user 内容是把刚生成的正文逐行 JSON 化（`source_lines`）。这段内容每章、每次都不同，**永远不可能命中缓存**，而且它排在一个同样每次不同的 system 指令之后。这是一笔固定的、无法通过布局优化回收的浪费。

---

## 4. 优化建议（按性价比排序，均不涉及本报告改动）

### 建议 1（最高收益）：重排 prompt，把稳定内容前置、可变内容后置
目标布局（从前到后，稳定 → 可变）：

```
system:  role + 门禁规则                （全局稳定）
user:
  1. 输出硬约束提醒 output_constraint     （全局稳定，上移到最前）
  2. 完整招标需求 / 评分标准全文           （全局稳定，见建议 2）
  3. 本 H2 项目背景 + 本 H2 评分板块归类    （H2 级稳定，同 H2 下逐字一致）
  4. 当前章节边界 scope_reference          （每章变化）
  5. 事实卡 / 节点撰写计划                 （每章变化）
  6. 章节任务卡 task_card                  （每章变化，放最后）
```

- 对连续扩写同一文件的场景，1~2 段对**所有章节**逐字一致 → 形成全局长公共前缀。
- 1~3 段对**同一 H2 下的所有 H4**逐字一致 → H2 内批量扩写时命中率大幅提升。
- 真正每章不同的内容集中在尾部，缓存失效点被推到尽可能靠后。

### 建议 2：重新评估"裁剪 vs 缓存"的取舍
裁剪的初衷是省输入 token，但如果上游按**缓存 token 打折计费**（DeepSeek 命中缓存约 1/10 价、多数自建 vLLM 缓存几乎零边际成本），那么：

> 把完整招标需求/评分标准放在稳定前缀里一次性缓存，可能比"每章裁剪出不同子集但每次全量重算"**更省钱、也更快**。

建议用真实计费模型跑一次对比（见建议 5），再决定是否对"稳定大块"关闭裁剪、只对"评分聚焦提示"保留裁剪。至少可以提供一个"稳定前缀 + 裁剪后的聚焦提示"的混合布局，兼顾两者。

### 建议 3：按 H2 分批扩写，放大 H2 级前缀复用
既然背景与评分归类已按 H2 缓存，批量生成时**按 H2 聚簇、同 H2 的 H4 连续发请求**，配合建议 1 的布局，可让上游缓存在"切换到下一个 H2 之前"持续命中第 1~3 段前缀。打乱顺序扩写会反复使这段前缀失效。

### 建议 4：把结构修复调用与主生成解耦（降低根因 E 的浪费）
`_request_numbering_structure` 的不可缓存是结构性的。可考虑：
- 优先用纯规则的 `repair_layout` 覆盖更多情况，减少触发模型修复的比例；
- 或把该调用切到更便宜的小模型（现已有 pruning/辅助模型通道），避免用主模型为不可缓存的请求付全价。

### 建议 5（前置必做）：补齐缓存观测
在落地任何改动前，先在 trace / timing 中记录每次请求返回的：
- `usage.prompt_tokens`
- `usage.prompt_tokens_details.cached_tokens`（或对应服务字段）
- 推算的命中率 `cached / prompt_tokens`

这样才能：① 确认当前命中率确实接近 0，② 量化每条建议的实际收益，③ 满足项目 Observability 约束，避免"凭感觉改 prompt"。

---

## 5. 结论

当前"扩写章节几乎不命中缓存"是**提示词布局问题**，不是服务配置问题：

1. 可变的章节内容被放在了 user 消息最前面（根因 A），公共前缀立刻断裂；
2. 上下文裁剪移除了唯一的稳定大块（根因 B），与缓存目标互相抵消；
3. 本可复用的 H2 级稳定内容被埋在可变内容之后（根因 C）；
4. 没有缓存提示、更没有命中率观测（根因 D）；
5. 后处理的结构修复调用天然不可缓存（根因 E）。

**最小且最高收益的动作**：先补观测（建议 5），再做 prompt 重排（建议 1）——仅调整段落拼接顺序即可，不改动任何生成逻辑与输出格式，符合"保持现有桌面架构、兼容现有配置"的约束。

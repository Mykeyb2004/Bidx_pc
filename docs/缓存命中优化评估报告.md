# 章节扩写阶段 Prompt 缓存命中率评估报告

> 分析对象：`bid_writer/ai_writer.py`（提示词拼装与模型请求）、`bid_writer/context_pruner.py`（上下文裁剪）
> 结论先行：问题不是"没开缓存"，而是**请求的 token 前缀在每个章节之间几乎没有公共部分**，导致上游推理服务（vLLM / DeepSeek / 兼容 OpenAI 的网关）的 **prefix/KV 缓存无法命中**。本报告只做评估与建议，不改动代码。

---

## 1. 缓存命中的前提

所有兼容 OpenAI 的推理服务的 prompt 缓存（prefix cache / context cache / KV cache）都遵循同一条规则：

> **只有从第 0 个 token 开始、与上一次请求完全逐字节一致的最长公共前缀，才能被复用。**
> 一旦某个位置的内容发生变化，该位置之后的所有 token 都必须重新计算，缓存失效。

因此命中率取决于一件事：**稳定、可复用的大块内容是否被放在 messages 的最前面，变化的小块内容是否被放在最后面。**

当前代码恰好相反。

---

## 2. 当前请求的实际结构

`prepare_generation()`（`ai_writer.py:1214`）组装的请求是：

```
messages = [
  { role: "system", content: system_prompt },      # 稳定：role + 门禁规则
  { role: "user",   content: prompt }               # 见下方拼装顺序
]
```

`user` 内容由 `build_prompt_result()` 按固定顺序拼接（`ai_writer.py:1054-1091`）：

| 顺序 | 段落 | 稳定性 | 来源 |
|---|---|---|---|
| 1 | `chapter_context`（## 当前章节边界及招标/评分要求） | **高度变化** | 每章不同 |
| 2 | `output_constraint_reminder`（## 输出硬约束提醒） | 稳定（除 extra_rules） | 全局固定 |
| 3 | `fact_card_context` | 变化 | 选中的事实卡 |
| 4 | `node_writing_plan` | 变化 | 节点撰写计划 |
| 5 | `task_card`（## 章节任务卡） | 变化 | 每章路径/焦点/字数 |

关键在于第 1 段 `chapter_context` 内部的构造（`_build_chapter_context_section`, `ai_writer.py:429`）：

```
## 当前章节边界及招标/评分要求
### 招标需求参考      ← 仅 full_context 模式有；pruned 模式为空
### 项目背景参考      ← 按 H2 变化
### 评分要求          ← 按章节检索结果变化（pruned 模式每章不同）
### 当前章节边界      ← scope_reference，每章必不同（父标题/本标题/同级标题）
```

---

## 3. 根因分析（为什么几乎不命中）

### 根因 A：可变内容被放在 user 消息的最前面
`user` 消息第一段就是 `chapter_context`，而它内部**第二行之后就开始出现每章不同的内容**（项目背景、检索到的评分项、章节边界）。这意味着：

- `system` prompt 之后，公共前缀**立刻断裂**。
- 可缓存的前缀实际上只剩下 `system_prompt` 本身 + `"## 当前章节边界及招标/评分要求\n"` 这一行标题。
- `system_prompt` 通常只有几百~一两千 token，相对每次请求的总输入占比很小，缓存收益极低。

### 根因 B：上下文裁剪（pruned/auto 模式）让"稳定大块"消失
在默认的裁剪路径下（`context_pruner.build_context`），`bid_requirements` 和完整 `scoring_criteria` **不进入 prompt**，取而代之的是**每章各异的检索子集**（`scoring_section`）。

- 在 `full_context` 模式下，至少 `### 招标需求参考 + 完整招标需求`（大块、稳定）排在 `chapter_context` 靠前位置，还能形成一段可观的公共前缀；
- 但一旦启用裁剪，这段最大的稳定内容被拿掉，剩下的全是每章不同的小块，**公共前缀被进一步压缩到几乎为零**。

换句话说：裁剪优化了单次请求的 token 数，却**顺带摧毁了跨章节的缓存复用**。两者在当前布局下是互相抵消的。

### 根因 C：同一 H2 下的 H4 章节本可共享的前缀没有被利用
系统已经在 H2 级别缓存了两类昂贵结果（本地缓存，命中良好）：
- `H2ProjectBackgroundGenerator`（项目背景，H2 级）
- `_classify_scoring_with_h2_cache`（评分分类，H2 级）

也就是说，**同一个 H2 下的多个 H4 章节，其"项目背景"和"评分板块归类"是完全相同的**。这是一段天然可复用的、每章之间逐字节一致的内容。但当前布局把它夹在 `chapter_context` 中间、且排在每章不同的 scope_reference 之前，导致这段本可命中的前缀同样无法被上游缓存利用。

### 根因 D：请求里没有任何缓存提示，也没有观测
- `_build_request_options()`（`ai_writer.py:328`）只设置 `model/messages/temperature/max_tokens/stream/top_p/seed/reasoning_effort`，**没有任何 `cache_control` / `extra_body` 缓存开关**。对自动前缀缓存的服务（DeepSeek、多数 vLLM 网关）这不是必需的，但对需要显式声明的服务（如 Anthropic 风格 `cache_control`）则完全没用上。
- trace / timing 日志中**没有记录 `usage.prompt_tokens_details.cached_tokens`** 一类字段（`generation_trace.py`、`timing_logger.py` 均无）。因此目前"缓存几乎没命中"只能靠主观感受，无法量化，也无法验证优化效果——这违反了项目 `Observability` 约束。

### 根因 E：每章的第二次模型调用天然不可缓存
`_request_numbering_structure()`（`ai_writer.py:507`）在正文后处理阶段会用**主模型**再发一次请求，其 user 内容是把刚生成的正文逐行 JSON 化（`source_lines`）。这段内容每章、每次都不同，**永远不可能命中缓存**，而且它排在一个同样每次不同的 system 指令之后。这是一笔固定的、无法通过布局优化回收的浪费。

## 4. 优化建议（按性价比排序，均不涉及本报告改动）

### 建议 1（最高收益）：重排 prompt，把稳定内容前置、可变内容后置
目标布局（从前到后，稳定 → 可变）：

```
system:  role + 门禁规则                （全局稳定）
user:
  1. 输出硬约束提醒 output_constraint     （全局稳定，上移到最前）
  2. 完整招标需求 / 评分标准全文           （全局稳定，见建议 2）
  3. 本 H2 项目背景 + 本 H2 评分板块归类    （H2 级稳定，同 H2 下逐字一致）
  4. 当前章节边界 scope_reference          （每章变化）
  5. 事实卡 / 节点撰写计划                 （每章变化）
  6. 章节任务卡 task_card                  （每章变化，放最后）
```

- 对连续扩写同一文件的场景，1~2 段对**所有章节**逐字一致 → 形成全局长公共前缀。
- 1~3 段对**同一 H2 下的所有 H4**逐字一致 → H2 内批量扩写时命中率大幅提升。
- 真正每章不同的内容集中在尾部，缓存失效点被推到尽可能靠后。

### 建议 2：重新评估"裁剪 vs 缓存"的取舍
裁剪的初衷是省输入 token，但如果上游按**缓存 token 打折计费**（DeepSeek 命中缓存约 1/10 价、多数自建 vLLM 缓存几乎零边际成本），那么：

> 把完整招标需求/评分标准放在稳定前缀里一次性缓存，可能比"每章裁剪出不同子集但每次全量重算"**更省钱、也更快**。

建议用真实计费模型跑一次对比（见建议 5），再决定是否对"稳定大块"关闭裁剪、只对"评分聚焦提示"保留裁剪。至少可以提供一个"稳定前缀 + 裁剪后的聚焦提示"的混合布局，兼顾两者。

### 建议 3：按 H2 分批扩写，放大 H2 级前缀复用
既然背景与评分归类已按 H2 缓存，批量生成时**按 H2 聚簇、同 H2 的 H4 连续发请求**，配合建议 1 的布局，可让上游缓存在"切换到下一个 H2 之前"持续命中第 1~3 段前缀。打乱顺序扩写会反复使这段前缀失效。

### 建议 4：把结构修复调用与主生成解耦（降低根因 E 的浪费）
`_request_numbering_structure` 的不可缓存是结构性的。可考虑：
- 优先用纯规则的 `repair_layout` 覆盖更多情况，减少触发模型修复的比例；
- 或把该调用切到更便宜的小模型（现已有 pruning/辅助模型通道），避免用主模型为不可缓存的请求付全价。

### 建议 5（前置必做）：补齐缓存观测
在落地任何改动前，先在 trace / timing 中记录每次请求返回的：
- `usage.prompt_tokens`
- `usage.prompt_tokens_details.cached_tokens`（或对应服务字段）
- 推算的命中率 `cached / prompt_tokens`

这样才能：① 确认当前命中率确实接近 0，② 量化每条建议的实际收益，③ 满足项目 Observability 约束，避免"凭感觉改 prompt"。

---

## 5. 结论

当前"扩写章节几乎不命中缓存"是**提示词布局问题**，不是服务配置问题：

1. 可变的章节内容被放在了 user 消息最前面（根因 A），公共前缀立刻断裂；
2. 上下文裁剪移除了唯一的稳定大块（根因 B），与缓存目标互相抵消；
3. 本可复用的 H2 级稳定内容被埋在可变内容之后（根因 C）；
4. 没有缓存提示、更没有命中率观测（根因 D）；
5. 后处理的结构修复调用天然不可缓存（根因 E）。

**最小且最高收益的动作**：先补观测（建议 5），再做 prompt 重排（建议 1）——仅调整段落拼接顺序即可，不改动任何生成逻辑与输出格式，符合"保持现有桌面架构、兼容现有配置"的约束。

---

## 6. 代码优化方案（可落地）

按依赖顺序分三步：先建观测基线 → 再重排前缀 → 最后处理裁剪取舍与边角浪费。每步独立可验证、可回滚。

### Step 1：缓存命中观测（前置，必须先做）✅ 已实现

> 实现落点：`config.report_usage`（`BID_WRITER_REPORT_USAGE`，默认开）、`ai_writer._build_request_options` 流式加 `stream_options`、`ai_writer._extract_cache_usage` / `_log_cache_usage`、流式与同步路径均落 `prompt_cache_usage` 日志。测试：`tests/test_prompt_cache_usage.py`（4 条，全绿）。

**目标**：在 trace 与 timing 中记录每次请求的输入 token 数与命中缓存 token 数，拿到当前基线（预期命中率≈0），并作为后续每步的验收口径。

**1.1 流式请求需显式开启 usage 回传**
OpenAI 兼容流式默认不返回 `usage`，必须加 `stream_options`。在 `_build_request_options()`（`ai_writer.py:328`）里：

```python
def _build_request_options(self, messages: list, stream: bool) -> dict:
    options = {
        "model": self.config.model,
        "messages": messages,
        "temperature": self.config.temperature,
        "max_tokens": self.config.max_tokens,
        "stream": stream,
    }
    if stream:
        # 让流式最后一个 chunk 带回 usage（含 cached_tokens）
        options["stream_options"] = {"include_usage": True}
    ...
    return options
```

> 注意：个别网关不支持 `stream_options`。应做成可开关（新增 `BID_WRITER_REPORT_USAGE`，默认开），并对返回里缺字段的情况静默降级，不得影响生成。

**1.2 从响应中提取 usage**
- 同步路径 `_sync_expand_raw`：`response.usage` 直接可读。
- 流式路径 `_stream_expand_raw`：`usage` 只出现在最后一个 `chunk.usage`（此时 `chunk.choices` 常为空，现有代码 `if not chunk.choices: continue` 会跳过——需在 `continue` 前先抓 `chunk.usage`）。

抽一个纯函数，避免散落：

```python
@staticmethod
def _extract_cache_usage(usage: Any) -> dict[str, int]:
    """从 usage 对象提取 prompt/cached token，兼容不同服务字段。"""
    if usage is None:
        return {}
    prompt = getattr(usage, "prompt_tokens", 0) or 0
    details = getattr(usage, "prompt_tokens_details", None)
    cached = 0
    if details is not None:
        cached = getattr(details, "cached_tokens", 0) or 0
    # DeepSeek 风格兼容
    cached = cached or getattr(usage, "prompt_cache_hit_tokens", 0) or 0
    hit_rate = round(cached / prompt, 4) if prompt else 0.0
    return {"prompt_tokens": prompt, "cached_tokens": cached, "cache_hit_rate": hit_rate}
```

**1.3 落日志**
在 `_stream_expand_raw` 的 `finally`（`ai_writer.py:1483`）与 `_sync_expand_raw` 返回前，调用 `write_timing_log("prompt_cache_usage", **self._extract_cache_usage(usage))`。可选：在 `GenerationTraceSession.finalize` 增加一个 `cache_usage` 字段写入 summary（`generation_trace.py:281` 的 `_build_summary`）。

**验收**：连续扩写 3+ 章节，`generation_timing.log` 出现 `prompt_cache_usage` 事件，确认 `cache_hit_rate` 当前接近 0。

**采集基线的操作**：
1. 确认未关闭观测（`BID_WRITER_REPORT_USAGE` 不设或设为 `1`）；
2. 用 `uv run python run.py` 正常扩写**同一 H2 下连续 3 个以上章节**；
3. 读 `log/generation_timing.log` 里 `"event": "prompt_cache_usage"` 的行，记录每条的 `prompt_tokens` / `cached_tokens` / `cache_hit_rate`；
4. 这组数字即 Step 2/3 的对照基线。若此时 `cache_hit_rate` 已明显 >0，说明上游本就在缓存，Step 2 收益会更直接；若恒为 0，需确认网关是否支持 `stream_options`/前缀缓存（个别网关不支持时字段会缺失，日志不会出现该事件）。

> **当前进度（2026-10-22）**：Step 1 已实现并通过全部测试（785 passed）。按既定分步验收原则，**Step 2 等待上面这组基线数据后再动手**——因为重排会改变模型实际输入，输出质量只能靠真实生成样本对比确认，不能盲改。Step 3/4 同样排在 Step 2 之后。

#### 首次实跑发现并修复的一个 Step 1 bug（流式 usage 捕获）

用 `config_westlake.yaml`（网关 `ai.router.team`，模型 `gpt-6.1-sol`）实跑后，`generation_timing.log` 里**没有出现任何 `prompt_cache_usage` 事件**。排查结论：

- 探针直连网关证实：该网关**支持** `stream_options`，流式会返回 `usage.prompt_tokens_details.cached_tokens`。所以不是网关能力问题。
- 根因在 Step 1 自身代码：流式 reader 一旦读到 `finish_reason` 就立即 `return`。但按 OpenAI 规范，携带 usage 的那个 chunk（`choices` 为空）出现在 **finish_reason chunk 之后**，是整条流的最后一个 chunk。reader 提前退出，永远读不到它 → `usage_holder` 为空 → 不记日志。

**修复**：reader 见到 `finish_reason` 后不再立即 `return`，而是记下原因、继续把流读到自然结束（从而捕获尾随 usage chunk），再发出 `finish` 事件。由于 reader 在发 `finish` 之前就已写入 `usage_holder`，主循环的 `finally` 读到它时无竞态。新增回归测试 `test_stream_captures_trailing_usage_chunk`（精确复现"finish 在前、usage 在后"的 chunk 顺序），并已用真实网关端到端验证可取到 `prompt_tokens=11, cached_tokens=0`。

#### 实测基线（config_westlake.yaml / ai.router.team / gpt-6.1-sol，2026-10-22 重跑）

同一 H2（14.4）下连续 3 个章节：

| 章节 | prompt_tokens | cached_tokens | 命中率 |
|---|---|---|---|
| 14.4.1 | 2140 | 0 | 0.0 |
| 14.4.2 | 6370 | 0 | 0.0 |
| 14.4.3 | 6362 | 0 | 0.0 |

对 3 条 prompt 做前缀 diff：
- **system prompt 2070 字，三章完全一致**（共同前缀 = 全长），排在消息数组最前；
- **user 消息共同前缀仅 73 字**就断裂——因为 user 第一段就是每章不同的 `### 当前章节边界`（上级/本章/同级标题）。

**关键验证**：单独做了"同一超长 prefix 连发 3 次"的探针：
- 第 1 次 `cached=None`、第 2 次 `cached=None`、**第 3 次 `cached=1384/1586`**。

结论修正（比第 3 节更精确）：
1. **该网关确实支持前缀缓存**，但**是惰性 / 需预热的**——同一前缀要被连续命中若干次才开始打折；
2. 真实 3 章跑出全 0，是因为①真正共享的只有 2070 字 system，②3 次命中对这个网关的预热而言是临界值，还可能被路由分散到不同后端实例；
3. 因此 **Step 2（拉长稳定前缀）收益被证实**：把完整招标需求 + H2 共享背景并入前缀后，一旦预热命中，被打折的 token 会从"2070 字 system"扩大到"几千字稳定块"，量级完全不同。同时**按 H2 聚簇、连续批量扩写**能帮助缓存预热（见建议 3）。

> 基线已采集完毕，Step 2 的前提（网关支持缓存 + 当前前缀过短）均已被实测证实，可以推进 Step 2。

#### ⚠️ 关键修正：该网关（ai.router.team）的前缀缓存不可靠（2026-10-22 二次实测）

Step 2 重排完成后，用 `config_westlake.yaml` 重跑同 H2 的 3 章（21:10~21:11），**6 条 `prompt_cache_usage` 全部 `cached=0`**，重排后共享前缀变长也没带来命中。进一步做了两组对照探针（同一超长固定前缀）：

| 场景 | 结果 |
|---|---|
| 首次探针：3 次背靠背相同前缀 | 第 3 次命中 `cached=1384/1586` |
| 复测 A：4 次背靠背相同前缀 | **全部 0 命中** |
| 复测 B：3 次相同前缀，间隔 20s | **全部 0 命中**，且末次 `prompt_tokens` 异常飙到 28322 |

结论：**那次唯一命中不可复现**。这种非确定性正是 **router / 聚合型网关**的典型特征——`ai.router.team` 把请求负载均衡到多个后端实例，前缀/KV 缓存是**每实例、每进程**的，下一次请求很可能落到另一台实例，于是上一次的缓存不存在。末次 token 数突然暴涨也佐证了路由不稳定（被路由到了对上下文计费完全不同的后端）。

**这把瓶颈从"prompt 布局"上移到了"网关路由"**：
- Step 2 的重排本身是正确的、已完成、无副作用，但**在这个网关上无法转化为稳定的缓存收益**，因为命中与否由路由决定，不由前缀长度决定；
- Step 3（把招标需求/评分全文放进稳定前缀）在这个网关上**同样无法带来可靠收益**——再长的稳定前缀，落到不同实例一样是冷启动。继续做 Step 3 来省缓存，对当前网关是无效投入。

**要让缓存优化真正生效，必须换一个提供稳定前缀缓存的后端**，三选一：
1. **直连会自动缓存的厂商**：如 DeepSeek 官方（`prompt_cache_hit_tokens` 按次计费打折）、OpenAI 官方（自动 prefix cache）、Anthropic（需 `cache_control`，另见下）；
2. **自建/独占一个 vLLM 实例**（`--enable-prefix-caching`），单实例无路由分散，KV 缓存稳定复用；
3. 若 `ai.router.team` 支持**会话亲和 / sticky routing / 指定单一 upstream** 的参数，固定到同一后端。

在换到上述任一后端之前，Step 1 的观测继续有效（能第一时间看出缓存是否开始命中），而 Step 2 的布局已经就位、等待一个"会缓存的后端"来兑现收益。

### Step 2：Prompt 前缀重排（核心收益）✅ 已实现（最小版）

> 实现落点：`ai_writer.build_prompt_result` 把全局稳定的 `output_constraint_reminder` 段移到 user 消息**最前**（原本在每章变化的 `chapter_context` 之后）；`_PROMPT_CONTRACT_BLOCKS` 顺序同步调整；测试快照已更新。**仅改段落顺序，未改任何段落文本与输出格式。** 测试：全套 785 passed。
>
> **实测效果（config_westlake，同 H2 连续 3 章）**：system+user 共同前缀从重排前 **2143 字**（system 2070 + user 仅 73）增长到 **2334 字**（多出的 264 字即 `output_constraint_reminder`，现已进入可复用前缀）。
>
> **诚实说明**：此配置跑在 pruned 模式，`bid_requirements` 与项目背景都未进 prompt，可前置的稳定块只有 `output_constraint_reminder`，所以本步增益有限（user 侧共享前缀 73→264 字）。**量级更大的收益依赖 Step 3**（把完整招标需求/评分标准放进稳定前缀）。两步叠加才能把"几千字稳定块"全部纳入可缓存前缀。
>
> **质量验收提示（需你来做）**：重排改变了模型实际看到的段落顺序（约束提醒现在在章节边界之前）。请用 `config_westlake.yaml` 重跑同样几章，和 `log/generation_traces/` 里 20:56~20:57 的旧样本对比正文质量；若有退化，`git revert` 本次改动即可回滚（纯顺序变更，无数据风险）。

**目标**：把稳定内容前置、可变内容后置，让公共前缀尽可能长。**只改拼接顺序，不改任何段落的生成函数、不改输出格式。**

当前拼接顺序（`build_prompt_result`, `ai_writer.py:1054-1091`）：
`chapter_context → output_constraint_reminder → fact_card → node_writing_plan → task_card`

**2.1 把全局稳定段提到最前**
`output_constraint_reminder`（除 `prompt_extra_rules` 外全局固定）应移到 user 消息第一段。调整 `_append_prompt_section` 的调用顺序即可。

**2.2 拆分 `chapter_context`，让稳定子块独立前置**
现在 `_build_chapter_context_section`（`ai_writer.py:429`）把 4 个稳定性不同的子块焊成一段，是命中率杀手。建议拆成独立 section，按稳定性插入：

```
user 段顺序（稳定 → 可变）：
  [S] output_constraint_reminder        # 全局稳定
  [S] bid_requirements / scoring 全文    # full_context 模式；见 Step 3
  [H] project_background（## 项目背景参考） # H2 级稳定
  [V] scope_reference（## 当前章节边界）   # 每章变化
  [V] scoring_section（评分聚焦）          # 每章变化（裁剪模式）
  [V] fact_card_context                   # 每章变化
  [V] node_writing_plan                   # 每章变化
  [V] task_card                           # 每章变化，放最后
```

实现上把 `_build_chapter_context_section` 内联的 `project_background` 和 `scope_reference` 抽成独立 `_append_prompt_section` 调用，删掉大标题 `## 当前章节边界及招标/评分要求` 这个把它们绑在一起的壳（或保留壳但只包可变子块）。

> **风险点**：prompt 文本结构变了，`test_prompt_contract.py` 与 trace 的 `prompt_contract_blocks`（`ai_writer.py:776` 的 block_specs）都基于 section 名与顺序。需同步更新 `_PROMPT_CONTRACT_BLOCKS` 的顺序与对应测试快照。这是本步主要工作量。

**2.3 校验前缀确实变长**
重排后同一 H2 下连续扩写两章，对比两次请求 `messages` 序列化后的最长公共前缀长度（可在 trace 的 `05_request_options.json` 上离线 diff）。预期从"仅 system"增长到"system + 全局稳定段 + H2 稳定段"。

**验收**：Step 1 的 `cache_hit_rate` 在同 H2 连续扩写场景明显上升（取决于服务，自建 vLLM 通常可达 30%~60%+）。

### Step 3：裁剪 vs 缓存的可配置取舍

> **前置条件（2026-10-22 更新）**：经二次实测，当前网关 `ai.router.team` 不提供可靠前缀缓存（见上文"关键修正"）。**在换到会稳定缓存的后端之前，Step 3 不应为"省缓存"而做**——它会改变模型实际输入（稳定全文 vs 裁剪聚焦），却换不到缓存收益，是净负投入。只有当 Step 1 观测显示新后端开始稳定命中（`cached_tokens > 0` 可复现）后，再评估 Step 3。

**目标**：让"稳定大块全文缓存"与"每章裁剪聚焦"不再互斥，可按计费模型择优。

**3.1 新增布局开关**（`config.py`，遵循现有 `BID_WRITER_*` 命名）
`BID_WRITER_STABLE_PREFIX_MODE`，取值：
- `pruned`（现状，默认）：只注入裁剪后的聚焦评分项；
- `full_stable`：把完整 `bid_requirements` + `scoring_criteria` 放入稳定前缀，裁剪结果降级为"评分聚焦提示"附在可变区；
- `auto`：按 token 阈值自动选择。

**3.2 混合布局**
在 `full_stable` 下，`build_prompt_result` 既输出稳定全文前缀（走 `_build_full_context_stable_prefix_sections`, `ai_writer.py:721`），又保留裁剪出的 `scoring_section` 作为可变区的"本章重点评分项"。即稳定区给全集、可变区给聚焦，两者并存。

**3.3 用 Step 1 的数据做 A/B**
同一批章节分别用 `pruned` 与 `full_stable` 跑，比较 `prompt_tokens`、`cached_tokens`、实际计费与耗时，再决定默认值。

**验收**：产出一张 A/B 对比表（token/命中率/成本/延迟），据此设定默认 `STABLE_PREFIX_MODE`。

### Step 4：降低结构性不可缓存浪费（可选）

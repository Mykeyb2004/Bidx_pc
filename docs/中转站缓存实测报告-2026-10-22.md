# 中转站缓存实测报告（2026-10-22）

## 结论

**当前主生成通道支持并实际报告了 prompt 缓存命中。** 使用 `.env.local` 的主生成地址、密钥、模型及采样参数，以 `curl` 连续发出 7 次请求，3 次重复请求均返回正数 `usage.prompt_tokens_details.cached_tokens`，包含普通和流式调用。

curl 阶段只能确认该中转通道返回了缓存命中信息。后续提供的后台 CSV 已进一步确认：缓存读取量与接口一致，并按普通输入单价的 5% 计费，详见文末补充核对。仍不能确定缓存位于中转站自身还是其上游；跨不同章节的稳定前缀复用效果仍需单独观测。

## 判断边界

1. **仅凭响应字段缺失不能断定零命中。** 请求 1、3、4、6 在 curl 响应中未返回缓存细项，上表保留初测时的“未知”。后续后台 CSV 对这四次均明确记录缓存读取为 0，见文末核对。
2. **HTTP 缓存与 prompt 缓存分别判断。** 所有响应的 `cf-cache-status` 都是 `DYNAMIC`，流式响应另有 `cache-control: no-cache`；它们描述 HTTP/CDN 行为，并不否定模型输入缓存。重复请求的响应 ID、创建时间及响应体哈希均改变，没有观察到原封不动重放整个 HTTP 响应的证据。
3. **速度不作为命中依据。** 流式重复请求 5 虽然命中，却比请求 4 更慢；可靠的正面证据是 `cached_tokens > 0`。
4. **同一模型名的输入计数有变化。** 只改少量尾部文字时，报告的输入 tokens 从 15798 变为 11586；本次无法解释该差异，可能涉及路由或计数方式。不能由此断定具体上游模型，也不能保证生产请求每次路由一致、每次都命中。
5. **计费已获后续记录支持。** 首轮 curl 未验证计费；后续后台 CSV 的输入、缓存读取、输出费用及最终费用均可按记录中的单价与分组倍率核算，详见文末。CSV 本身未标明币种。

## 补充：后台调用记录与计费核对

来源：仓库根目录 `usage-records-20261022-225827.csv`，共 31 条记录，其中 `User-Agent=curl/8.7.1` 恰好 7 条，全部 `SUCCESS`。

按时间顺序、输入总量、输出数量及缓存读取量逐条核对，7 条与本轮测试全部一致。后台时间与接口创建时间相差不超过 2 秒。CSV 的“会话ID”为 `derived_...`，与接口响应 `resp_...` 不是同一种标识，未将它们作为同一 ID 直接连接。

### 统计口径

CSV 的“输入Token”仅指未缓存输入，接口的 `usage.prompt_tokens` 包含缓存输入：

```text
CSV 输入Token + CSV 缓存读取Token = API prompt_tokens
CSV 输入Token + CSV 缓存读取Token + CSV 输出Token = CSV 总Token
```

例如请求 2：`182 + 15616 = 15798`；因此后台输入显示 182，与前端输入 15798 完全一致。

| 请求 | 后台时间 | CSV 行号 | 未缓存输入 | 缓存读取 | 最终费用 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1：首次 ALPHA | 22:54:59 | 8 | 15798 | 0 | 0.012662 |
| 2：完全重复 1 | 22:55:12 | 7 | 182 | **15616** | 0.000794 |
| 3：尾部改为 BETA | 22:55:16 | 6 | 11586 | **0** | 0.009293 |
| 4：尾部改为 GAMMA，流式 | 22:55:22 | 5 | 11586 | **0** | 0.009297 |
| 5：完全重复 4，流式 | 22:55:31 | 4 | 194 | **11392** | 0.000639 |
| 6：更换首部标识，DELTA | 22:55:40 | 3 | 15963 | 0 | 0.012842 |
| 7：完全重复 6 | 22:55:49 | 2 | 1883 | **14080** | 0.002142 |

行号包含表头。费用采用 CSV 原始单位，文件未注明币种。

### 计费是否实际采用缓存价格

从 token 数和各费用项反推，分组倍率之前每百万 tokens 的单价为：

- 普通输入：2。
- 缓存读取：约 0.1，因 CSV 费用保留六位小数存在舍入。
- 输出：10。

缓存读取单价为普通输入的 **5%**，即便宜 **95%**。分组倍率为 `0.4`，会员折扣率为 0，服务档位倍率为 1。按以下公式重算 7 笔记录，均在六位小数舍入误差内一致：

```text
最终费用 = (未缓存输入 × 2 + 缓存读取 × 0.1 + 输出 × 10) / 1000000 × 0.4
```

因此，后台计费记录确实采用了缓存低价。完整重复的普通请求从 `0.012662` 降到 `0.000794`，流式重复从 `0.009297` 降到 `0.000639`。

7 次请求合计输入 98280 tokens，其中缓存读取 41088，按输入量加权的缓存比例为 **41.81%**。最终费用合计 **0.047669**。若相同输入、输出均不命中缓存，按同一单价和倍率估算为 **0.078896**；本轮少计约 **0.031227（39.58%）**。这只是本轮构造测试的结果，不能直接外推为生产节省比例。

### 对原结论的补强与限制

- “当前通道有 prompt 缓存，并在重复请求中实际命中”与后台完全一致，计费证据也得到补齐。
- 请求 3、4 只改变长前缀之后的尾部，但后台缓存读取均为 0。当前证据支持完全重复请求命中，**尚不支持稳定前缀在不同章节请求之间必然复用**，也不能反推“调整提示词顺序就一定有效”。
- 三组完全重复请求各自共享一个后台会话ID，修改尾部后会话ID发生变化；这提供了后续检查会话、路由或缓存键策略的线索。CSV 无法证明会话ID决定了缓存命中，更不能据此认定服务只缓存完整请求。
- 所有请求的缓存写入数量和费用均为 0，不能用此否定自动 prompt 缓存；本轮正面证据来自明确记录的缓存读取及对应费用。
